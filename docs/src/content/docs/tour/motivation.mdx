I created Mace after repeatedly seeing configuration contracts split across a
data file, a schema format, application code, and prose documentation. Editors
could sometimes suggest fields, but the configuration language itself did not
know which values were valid or where injected values came from.

Mace asks a different set of questions:

1. Can the configuration's final shape be checked before it reaches the app?
2. Can externally supplied values enter the file with known names and types?
3. Can the same contract drive diagnostics, completion, and documentation?
4. Can evaluation remain deterministic and safe to inspect?

The language answers those questions with built-in schemas, explicit runtime
input contracts, typed immutable variables, and documentation metadata.

## Put the contract next to the configuration

Suppose a package configuration requires a name, version, development
dependencies, and production dependencies. Its contract can be published as a
Mace schema output:

```mace
// package-schema.mace
[output = 'schema']
{
  name: string /# Public package name,
  version: string /# Published package version,
  dev_dependencies: record<string> /# Development-only packages,
  dependencies: record<string> /# Runtime packages,
}
```

A data file loads and validates against that contract:

```mace
[output = 'data', schema_file = './package-schema.mace']
{
  name: "@example/widget",
  version: "1.0.0",
  dev_dependencies: {
    test_runner: "^2.0.0",
  },
  dependencies: {},
}
```

`record<string>` means that any valid identifier key is allowed but every value
must be a string. The `/#` descriptions are metadata for documentation-aware
tooling; changing them cannot change evaluation.

<Aside title="Schemas validate the final output">

A schema does more than improve autocomplete. Missing required fields, unknown
fields, and wrong value types stop processing, and Mace emits no partial record.

</Aside>

## Make injected values explicit

Template-driven configuration often uses names that only exist in external
documentation:

```yaml
name_template: "{{ .ProjectName }}_{{ .Version }}_{{ .Os }}_{{ .Arch }}"
```

Mace instead lets the host select a schema for runtime input:

```mace
// release-input.mace
[output = 'schema']
{
  project_name: string,
  version: string,
  os: string,
  arch: string,
}
```

```mace
[output = 'data', parse_file = './release-input.mace']
{
  name_template: "$($project_name)_$($version)_$($os)_$($arch)",
}
```

Before the second file evaluates, the host must provide a complete record that
satisfies the selected input schema. Its fields enter scope as `$project_name`,
`$version`, `$os`, and `$arch`, making their external origin visible in source
and to the language server.

A contract may also be an explicit HTTP(S) `.mace` URL:

```mace
[output = 'data', parse_file = 'https://pkg-releaser.example/input.mace']
{
  name_template: "$($project_name)_$($version)_$($os)_$($arch)",
}
```

Only imports and file directives resolve sources. Runtime expressions cannot
construct paths or initiate network requests.

## Prefer constraints over executable configuration

Mace deliberately omits loops, functions, mutation, shell execution, array
indexing, and arbitrary host calls. It provides enough expression behavior to
assemble a final record while keeping evaluation bounded and understandable.

That trade-off makes a Mace file useful as both configuration and contract:
applications receive validated data, authors receive precise diagnostics, and
tooling can explain the available structure without executing application code.
